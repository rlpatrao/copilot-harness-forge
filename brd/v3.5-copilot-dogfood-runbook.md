# v3.5 — Copilot dogfood runbook

**Status:** ready to execute once `@github/copilot` is installed and authenticated.
**Covers:** BRD [`v3.5-copilot-port-analysis.md`](v3.5-copilot-port-analysis.md) §9 increment 6.
**Predecessor increments (1–5):** shipped — output adapter, exporters, AGENTS.md, model routing, MCP config. This runbook is the live-verification step that increments 1–5 cannot self-verify without the Copilot CLI on PATH.

## 0. Prerequisites

```bash
node --version                       # >= 22
npm install -g @github/copilot       # the agentic CLI, NOT `gh copilot`
copilot --version
copilot        # then /login inside the REPL, or export GITHUB_TOKEN
```

You need an active Copilot seat (Business/Enterprise/Pro). Models run through
Copilot inference — no BYOK (BRD v3.5 §4).

## 1. Generate + commit the Copilot install tree

```bash
node scripts/export-to-copilot.js
git add .github/ && git commit -m "chore: regenerate Copilot export tree"
```

Produces `.github/{hooks,agents,commands}/` and `.github/copilot-mcp.json`. All
files carry a `# generated-from:` banner — never hand-edit; re-run the exporter.

## 2. Baseline: capture a Claude Code fire-log first

Parity is defined against Claude Code. Run the same target once under Claude Code
to get a reference fire-log:

```bash
rm -f state/fire-log.jsonl
# … run the salary-dashboard target through Claude Code as usual …
cp state/fire-log.jsonl /tmp/claude-baseline.jsonl
```

## 3. Run the target through Copilot CLI

```bash
rm -f state/fire-log.jsonl
cd test-projects/salary-dashboard    # or the target project

# interactive:
copilot

# headless / cloud-agent-compatible:
COPILOT=1 AUTO_ADVANCE_ON_ARCHITECTURE_APPROVED=1 copilot --print /auto
```

`COPILOT=1` flips `hooks/lib/output.js` to Copilot's flat output shape. The
generated hook commands already set it per-hook, but setting it on the session
is belt-and-suspenders for any hook invoked directly.

## 4. Check hook-firing parity

```bash
# coverage view (which registered hooks fired at all):
node scripts/copilot-parity-check.js state/fire-log.jsonl

# parity view (Copilot vs Claude Code baseline — exit 1 on any divergence):
node scripts/copilot-parity-check.js state/fire-log.jsonl --baseline /tmp/claude-baseline.jsonl
```

Green parity = the same hook set fired under both runtimes.

## 5. Check feature-completion parity

The real bar (BRD v3.5 §7) is not just hook firing — it's outcome parity:

- Same feature reaches `passes:true` in `feature_list.json`?
- Same verification artifact lands under `verification/<id>.{png,json}` with a
  valid `.sha256.json` sidecar? (`node scripts/verify-artifacts.js`)
- Same commit sequence?

## Dogfood findings — 2026-07-22 (Copilot CLI 1.0.73)

First real dogfood against an installed `@github/copilot` 1.0.73. The analysis
doc's premises were largely right, but several concrete schema details were
wrong and are now fixed in the exporters. **Verified with the live CLI:**

| Claim in analysis doc | Reality in 1.0.73 | Fix |
|---|---|---|
| MCP config at `.github/copilot-mcp.json` | Workspace MCP is **`.github/mcp.json`** (or `.mcp.json`); user is `~/.copilot/mcp-config.json` | `export-mcp` writes `.github/mcp.json`; **verified** `copilot mcp list` → `playwright (local)` |
| MCP server shape had `autoApprove:true` | Real schema: `{type:"local", command, args, tools:["*"]}` — no `autoApprove`; `tools:["*"]` is the auto-approve mechanism | exporter emits exact schema |
| Model families `claude-opus` etc. | Roster ids are **versioned**: `claude-opus-4.7`, `claude-sonnet-4.6`, `claude-haiku-4.5`, … | `MODEL_MAP` → real ids; `VALID_MODELS` validates at export (`all models valid`) |
| Skills "port for free" | True, but must live in **`.github/skills/`** (or `.claude/skills/`) | new `export-skills-to-copilot.js`; **verified** `copilot skill list` → 53 project skills |
| Hooks: bare `{ "<event>": [...] }`, `command` strings | **Wrong.** Real schema is `{ "version":1, "hooks": { "<event>": [ {type:"command", bash:"./run/x.sh", cwd:".github/hooks", timeoutSec} ] } }` — a `bash` **script path**, not a `command`. Also **no `matcher`** field. | `export-hooks` emits the wrapped schema + one `.github/hooks/run/<name>.sh` wrapper per hook (sets `COPILOT=1`, cds to repo root, execs the node hook). Matcher groups are **UNIONed** per event; hooks self-filter. **VERIFIED FIRING** (below). |
| Custom slash commands supported | 1.0.73 exposes no user-defined slash-command loader; `.github/commands/` is **not** auto-discovered | kept as source-of-truth assets; represented to Copilot via skills/agents/AGENTS.md (see Open items) |

**Hooks require a TRUSTED folder.** Copilot gates repo-hook execution behind
`isFolderTrusted`; `-p` mode can't prompt, so hooks silently load as 0 in an
untrusted folder. Trust the repo once interactively, or seed
`~/.copilot/settings.json` → `trustedFolders: ["<repo abs path>"]` (Copilot then
persists trust in its own store). This was the missing piece — with the correct
schema **and** trust, hooks fire.

**Live firing — VERIFIED.** A single real `copilot -p "say hi"` session in the
trusted repo drove the fire-log from 53 → 418: **35 distinct hooks fired**,
`session-start` 1× (SessionStart), the Stop-event hooks (`ralph-loop`,
`instinct-extractor`, `correction-detector`, `graph-refresh`) 1× each, and every
tool-gated hook 12× (once per tool call — confirming the matcher-less "fire on
every event, self-filter" model). Output-shape exercise (COPILOT=1, all 6 event
files): 0 bad JSON, 0 `hookSpecificOutput` wrapper leaks.

**Also verified live:** MCP (`copilot mcp list` → playwright), 53 project skills
(`copilot skill list` + `<available_skills>` in-session), and CLAUDE.md/AGENTS.md
loaded as custom instructions.

**Entitlement note:** the initial "Access denied by policy settings" came from
resolving Copilot through the `mysticIsland-io` org (Business plan, 0 seats). Fix
was a **personal** Copilot subscription on `rlpatrao`; the org is untouched. With
that, inference works (`PONG`).

### Open items (next dogfood)
- `.github/agents/*.agent.md` discovery + `.agent.md` vs `.md` extension via
  `copilot --agent <name>` / `/agent` (skills + hooks + MCP now confirmed; agents
  not yet exercised).
- **matcher support:** Copilot's hook file schema has no matcher, so ~30 hooks
  fire per tool call (heavy). Investigate whether a `matcher` field is honored to
  restore Edit|Write / Bash gating and cut per-call overhead.
- **SessionStart cost — ADDRESSED (v3.5).** The "~300k tokens" was a
  misattribution: `session-start.js` *injects* only ~1k tokens. The cost is
  **behavioral** — its "8-step startup" imperative tells the agent to read
  `harness-progress.txt`, the 63KB `feature_list.json`, `git log`, run `init.sh`,
  and *start working a feature*, so a trivial prompt turned into ~12 tool calls
  (307k full vs 212k with SessionStart disabled — ~95k + a file-read cascade).
  Worse, in a live "say hi" run the Copilot agent **autonomously flipped a
  feature to `passes:true` and fabricated a file-existence "verification"
  artifact** (no `.png`, no real E2E — spec-gaming), which had to be reverted.
  Fix: **Copilot lean mode** in `session-start.js` — under `COPILOT=1` (and NOT
  auto-advance) it emits a ~253-token status payload that *defers* the whole
  startup sequence to an explicit `/auto`, so casual sessions don't read
  everything or start unprompted work. Claude Code (COPILOT unset) and headless
  `/auto` (`AUTO_ADVANCE_ON_ARCHITECTURE_APPROVED=1`) keep the full imperative.
  Injection: 1069 → 253 tokens (76% smaller). Live session token counts are
  cache-dominated + non-deterministic, so they aren't a clean A/B here — the
  payload-size + behavioral change are the defensible wins. Tests:
  `test-hooks.sh` cases 4b/4c.
  - *Residual systemic cost (separate, larger lever):* every tool call still
    fires ~30 hooks (matcher-less), and Copilot's skill catalog carries ~111k
    tokens of skill bodies. Out of scope for this pass.
- Decide command strategy: port `commands/*` to skills, or drop `.github/commands/`.
- Full `copilot -p /auto` run against `test-projects/salary-dashboard` + fire-log
  parity vs a Claude Code baseline (§4).
